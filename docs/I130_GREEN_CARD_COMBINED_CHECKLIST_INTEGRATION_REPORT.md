# I-130 + Green Card (I-485) combined case type: integration report

Date: 2026-11-12

## Approach: reuse, no parallel engine
The Green Card (beneficiary) questionnaire from the uploaded checklist **already exists** in the codebase (`family-workflow/questionnaires/familyBasedImmigrantPetition.js`, `greenCard`; Residential/Employment history, Parents, Marital history, Prior spouse(s), Children, Public Charge, Documents list). It is the checklist the F1 family package already assigns on the adjustment-of-status path. Rather than duplicate it, the new case type reuses the exact F1 machinery:

- Visa type **"I-130 + I-485"** (label "I-130 + Green Card (I-485)"), family structure, two-party (petitioner + beneficiary), registered in `config/visaCategories.js`, `config/visaDropdown.js`, Admin `utils/visaOptions.js` (no Filing Path step at creation).
- Checklists (generated by the existing family loop, `questionnaires/familyChecklists.js`, `FAMILY_VISA_TYPES`): `i130_i130i485_petitioner_checklist` (petitioner), `green_card_i130i485_beneficiary_checklist` (beneficiary / Green Card applicant), `i864_i130i485_petitioner_checklist` (sponsor/petitioner); plus the optional, case-manager-approved NVC checklist and the I-130 beneficiary checklist (not auto-assigned on this path, as for F1).
- Filing path: createFamilyCase defaults `processingPath` to `ADJUSTMENT_OF_STATUS` for this type (only when none is supplied), which is what selects the Green Card + I-864 checklists and the I-485 package.
- Canonical ownership: the new keys reuse the existing path tables (`partyChecklistPaths.js` `FAMILY_CATEGORIES`, `partyChecklistPathsExtended.js` for the Green Card / NVC keys), so beneficiary answers stay under `beneficiary.*` and petitioner/sponsor answers under `petitioner.*`; no beneficiary value is copied into petitioner fields.
- Forms (same rows as F1, from `visaFormMappings.seed.js` / `checklistMappings.seed.js` / validator): I-130 (always), I-130A (spouse only), I-864 / I-864A / I-864EZ, I-485 (+ Supplement A), DS-260, I-765, I-131, I-693, gated by the existing processing-path and conditional rules. G-28 is not part of the F1 package and was not added.
- Nothing existing was changed: F1, K-1/K-3, I-824 and the standalone I-130 case type keep their definitions; only an added entry in each list. No timeline/reminder/autofill-precedence code was touched; no bulk migration.

## SUPERSEDED 2026-11-12 (final plan): I-485 is a single-person case type
The "Employment-Based Green Card" / "I-485 (Employment Based)" / "I-485 (Family Based)" two-party types were removed. There is ONE **I-485** case type: the registry's existing single-person "Adjustment of Status" (listed as "I-485" under Single applicant). It gets exactly two checklists, answered by the applicant (client role): `i485_green_card_checklist` (the existing Green Card checklist, canonical table = the family Green Card table) and `i485_i864_checklist` (the existing I-864 checklist, canonical table = the family I-864 table). Form rows (I-485, I-765, I-131, I-693, I-864) already existed and are now fed by these checklists. "I-130 + I-485" (renamed from "I-130 + Green Card (I-485)") and I-130 are unchanged. Not verified: that the existing I-485 form mappings read the Green Card answers under the client role; no DB-backed or end-to-end test was run.
