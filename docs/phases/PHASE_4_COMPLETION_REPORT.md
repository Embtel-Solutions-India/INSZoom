## Section 1 — Backend: New Lead Endpoints

**Investigation first established the actual Lead model shape and existing infrastructure** (contradicting several assumptions the prompt's own header made — see Section 6):

- `Lead.js` has **no `quizAnswers` field** — only `profileAnswers` (Mixed) and `criteriaAnswers` (a typed array specific to the scored public quiz). Both new endpoints store their raw answers in `profileAnswers`, per Step 7 Q2's own explicit instruction to "use the field that actually exists."
- `leadNumber` was not generated by either existing lead-creation function (`createLead`/`createQuizLead`) — confirmed by reading both — so `CaseNumberService.nextLeadNumber()` was added (Step 10, not skipped).
- `notifyStaffOfLead(lead)` already exists in `lead.service.js` and is shared by both pre-existing lead paths (in-app + push notification to `super_admin`/`admin`/`case_manager` via `notificationService.createForRoles`, plus a realtime socket emit). Both new endpoints reuse it directly rather than duplicating notification logic.
- **`publicQuizLimiter` (quiz.routes.js) is a local, unexported `const`** — cannot be imported. A new `publicLeadLimiter` was created in `lead.routes.js` with the identical configuration (`windowMs: 60000, max: 60`), per Step 12's own anticipated branch.

**Design decision, per Step 7 Q4's own framing as an open question:** `createLeadFromQuiz` is a **parallel function**, not a thin wrapper around `createQuizLead()`. The new endpoint's simpler `{contact, visaInterest, quizAnswers}` shape has no score to report, so it reuses only the notification mechanism (`notifyStaffOfLead`), not the scored-quiz-specific side effects.

## Section 6 — Unexpected Findings

1. **The prompt's own "Deliverable 4" summary and its detailed steps disagree about which endpoint the public quiz calls.** The summary bullet says "Public quiz → POST /api/leads → redirect to /consultation/book?leadId=", but Step 21 explicitly instructs confirming `EligibilityQuiz.jsx` is **unchanged** (still on `POST /api/eligibility-quiz/submit`, still redirecting to `/eligibility/results/:leadId`), and Step 25's own Flow 1 trace explicitly starts with `POST /api/eligibility-quiz/submit`, never mentioning `POST /api/leads`. I followed the detailed, doubly-corroborated instructions (Step 21 + Step 25) over the summary bullet: `EligibilityQuiz.jsx` was left completely untouched, and `POST /api/leads` was built per the explicit Steps 11–14 but has no current frontend caller. This is intentional, not an oversight — flagging it clearly rather than silently picking an interpretation.
2. **`Lead.quizAnswers` does not exist**, contradicting the prompt's own "Absolute Invariant" header ("Quiz answers and intake answers go into `Lead.quizAnswers` ONLY"). The prompt's own Step 7 Q2 correctly anticipated this exact possibility and instructed using whatever field actually exists — `profileAnswers` (a pre-existing generic Mixed field) was used for both new endpoints' raw-answers payload.
3. **Deliverable 3 (`POST /api/leads/:leadId/consultation`) already exists in substance, under a different path and module.** `POST /consultation/book` (in the pre-existing, fully-built `consultation` module — not `leads`) already accepts an optional `leadId`, finds the Lead, creates a real `Appointment`, sets `lead.consultationId`, updates `lead.status`, sends the prospect a confirmation email, and notifies the host/admin — everything Deliverable 3 asks for. `BookConsultation.jsx` is already fully wired to it. Per Step 16's own explicit "check first" branch, no new endpoint was built. **One literal mismatch, deliberately not changed:** the existing code sets `lead.status = "booked"` (a pre-Phase-2 enum value), not `"consultation_requested"` (the new Phase-2-added value Deliverable 3's template names). Changing that string would be a behavior change to a currently-working, already-shipped booking flow with unknown downstream consumers (e.g. the INSZoom admin Leads Inbox filtering/display on this exact status), for a purely cosmetic naming difference — left as-is rather than risk breaking something outside this phase's stated scope to verify.
4. **`publicQuizLimiter` cannot be imported** — it's a local, unexported `const` inside `quiz.routes.js`. A new limiter with identical configuration was created in `lead.routes.js` instead, exactly per Step 12's own anticipated fallback.
5. **`lead.routes.js`/`lead.controller.js` never used the shared `middleware/validate.js` pattern** other modules (e.g. `auth.routes.js`) use — they have their own inline `validationFailed(req, res)` helper. New code follows that existing convention rather than introducing a second validation pattern into the same file.
