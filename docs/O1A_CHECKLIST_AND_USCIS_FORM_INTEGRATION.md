# O-1A checklists, form mapping, autofill and downloads - implementation report

## 1. Existing implementation and what changed
- Before: O-1A cases were served by the shared `o1_employer_checklist` / `o1_employee_checklist` pair (ids `6a8e19f38dd95fb60a0ae053` / `...ae09b`), which carried O-1A and O-1B criteria behind a variant selector.
- Now: O-1A has a **dedicated pair**, built with the same shared builder as the O-1B / EB-1C / TN pairs: `o1a_employer_checklist` (19 questions) and `o1a_employee_checklist` (46 questions = 23 supplied questions + 2 conditional follow-ups (dependent count, denial explanation) + 11 documents + 10 criteria, one section per criterion). The shared pair now serves only bare "O-1"; neither it nor the O-1B pair matches O-1A, so a new O-1A case can never receive two versions.
- Existing cases keep the checklist references, responses, answers and files they already have (none were found for O-1A; the one O-1B case is untouched). No old answer was auto-mapped by label similarity. Stored templates were brought in line with the code by `scripts/syncChecklistDefinitions.js` (run it once on deploy for `o1a_*`, `o1_*`, `o1b_*`).

## 2. Questions, types and canonical paths (all optional: `required:false`, `metadata.optional`)
- Employer E1-E19: exact wording; company address is a **structured address** (`petitioner.company.address`); year = four-digit number; employee count = integer >= 0; income/salary = currency; website = URL; job locations = **repeatable structured records** (street, apartment/suite, city, state/province, ZIP/postal, country, company/end-client name); documents: Articles of Incorporation, Business License, "Blank Letterhead in word format" (`petitioner.company.documents.blankWordLetterhead`).
- Employee: exact wording for all supplied questions; other names = repeatable list; country of birth / citizenship = country selector (full list); SSN = text flagged `sensitive`; latest prior petition number, SEVIS, EAD number added; current U.S. address and foreign address = structured addresses, with consulate + foreign address in the section "Complete the following, if applying from Outside the USA."; Yes/No questions are radios stored as real booleans on their canonical paths; dependent count shows only when "dependents" = Yes; denial explanation only when "denied" = Yes.
- 11 documents with the exact labels (including "Copy of updated resume (We have )" - shown as supplied; nothing is auto-marked complete) and 10 criteria with the exact descriptions, each its own multi-file upload (`beneficiary.o1aEvidence.criterionN...`). Evidence uploads stay in the Document / case-evidence workflow; none is written into a PDF field.
- Scalar answers reuse the existing shared paths (`person.*`, `contact.*`, `immigration.*`, `company.*`, `employment.*`) so every form keeps working; the generic party layer exposes them as `beneficiary.*` / `petitioner.*`. New paths (registered in `o1aCanonicalPaths.js`) exist only where no equivalent did.

## 3. Forms and mapping
- Registry: I-129 + O/P supplement come with the case; DS-160 is a DOS reference row (no USCIS template); I-539 and I-907 are conditional; **G-28 conditional row added for O-1A**. Checklist mappings point at the o1a pair.
- I-129 party mapping gained two verified rules: `beneficiary.latestPriorPetitionNumber` -> `Line1_ReceiptNumber` (page 2) and `beneficiary.eadNumber` -> `Line5_EAD` (page 3) (new mapping version 17, activated). Beneficiary / petitioner facts (name, DOB, SSN, A#, SEVIS, US address, company, signatory, FEIN, wages, ...) fill every field that repeats them (see TN report for the rule engine).
- Structured address answers are flattened to the generic fields by the party layer (`beneficiary.currentUSAddress` -> address/apartment/city/state/zipCode; `petitioner.company.address` -> petitioner.address.*) without overwriting existing values.
- Unmapped, left for review (no verified one-to-one PDF field): foreign address and consulate, job-location records (only structured in the profile), dependents count, evidence documents.
- Yes/No answers: the canonical transformer now coerces the explicit yes/no checklist paths to booleans (some of those paths also contain words the date/country rules would have caught).

## 4. Persistence, approval, Admin sync
Same infrastructure as the other employer-sponsored visas: answers in `Answer`, documents in the Document model keyed by `documentType == question key`, drafts until a case manager approves (`checklist-gate.js`); an employee case inherits the approval of the employee checklist given on the employer case; the Admin Portal reads the same stored answers and canonical profile. Large uploads use the chunked path built earlier (700 KB chunks).

## 5. Verification (manual regression - no Playwright, no new e2e test)
- Automated content tests: `o1aChecklists.test.js` (8, DB-free: exact wording, types, conditions, optionality, booleans, address flattening); updated `o1VisaChecklists`, `o2Checklists`, `o1bChecklists` tests and the count guards (34 -> 36). Result: 86/86 across the checklist suites and `partyMapping.test.js`.
- Manual script against the real database (temporary data deleted afterwards): see section 6.

## 6. Manual regression results (real database, temporary data deleted afterwards: 4 cases, 0 leftover users)
PASS: employee case linked to employer case; I-129 assigned exactly once (+ its O/P supplement; I-907 present as before; G-28 / I-539 / DS-160 not auto-created); question counts 19 / 44 visible (+2 conditional follow-ups shown once answered); every question optional; client blocked before approval and able to open the employee checklist after the employer-case approval (inherited); employer answers restored including the structured address and both job locations; employee answers restored including other names, dependents count and denial explanation; an unanswered Yes/No stays unknown; partially filled checklists can be submitted; canonical beneficiary identity + flattened U.S. address; Yes/No stored as real booleans; petitioner name, signatory and flattened company address; PDF downloads (not the blank template) with beneficiary name, petitioner name and address (street/city/ZIP), beneficiary U.S. address, prior petition number and EAD number filled; a manual override survives re-autofill; O-1B still gets only its own pair.
Items the run flagged (not caused by this work, reported rather than changed): every O-1A case ALSO receives the older single-party **o1a_questionnaire** ("O1A Questionnaire", 9 sections, several questions required) from questionnaire.service.js VISA_TEMPLATE_DEFINITIONS. It predates this task and is intentionally retained by the registry seed notes, but it duplicates the topic of the new checklist and contains required questions. Retiring it for O-1A is a one-line decision for you (remove O1A from its visa scope); I did not do it without your say-so.

## 7. Limitations / manual review
- Foreign address, consulate, dependents and job-location records are preserved in the profile but not written to I-129 fields (no verified one-to-one field).
- SSN is stored through the existing profile path and flagged sensitive on the question; masking in the UI relies on the existing sensitive-field handling.
- No new automated end-to-end test was added, per instruction; regression was manual.
