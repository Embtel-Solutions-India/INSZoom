### Changes from rev 9

**C1. Acceptance is automatic; there is no manual evidence step.** Rev 9 (decisions 9, 18; "Evidence workflow"; "Responsibilities, separation of duties and audit"; Release 0b readiness) had `admin`/`team_lead` submit a URL and quote, confirm explicitly, with a different person accepting (four-eyes). The user decided that nobody submits anything: the system finds the official page or PDF, fetches it and records the decision itself. Consequences: the machine actor is `{userId: null, role: "system", label: "pipeline:official_source"}`; the manual routes (`POST /evidence`, `GET /evidence/:id`, `POST /evidence/:id/decision`) are **no longer routed** (the service code and its tests remain as internal code); the API is now `GET /editions`, `GET /gate`, `POST /auto-check` (the same automatic check on demand), exactly `admin`/`team_lead`, `super_admin` still excluded; the Admin screen has a **Check now** button and no URL/quote form; the four-eyes rule no longer applies because no human accepts.

**C2. "Acceptance is never inferred from silence" (decision 9, round 6/8/9 wording, Rule D "constant false until validated fixtures") is replaced by the user's rule:** the edition USCIS publishes as current is the accepted one unless USCIS says otherwise. `FilingEligibilityStatement` (`filingEligibility.js`) now recognises, each quoted verbatim from the source: `current_acceptable_edition`, `explicit_accept`, `explicit_not_accept` (a refusal always wins; accepted + refused for one edition is ambiguous and stays held), **`current_official_edition`** (the page's own "Edition Date" equals the edition and nothing refuses it) and **`current_official_pdf`** (for forms with no page of their own: the official PDF at its stable uscis.gov address prints the edition in its footer). An older edition that is not the current one is still held. Effective dates are never taken from a page. Verification stays mandatory and fail-closed: official https uscis.gov source, fresh fetch, the page/PDF names the edition, the template's edition matches; a compared PDF checksum that differs always holds the edition; where no checksum can be compared, the stored PDF's own footer must print the edition. A decision is written only when one is recorded (snapshot, five audit events, decision row); every other outcome is read-only.

**C3. The edition printed in the footer of the PDF is the edition.** Rev 9 treated the page date, effective date and `version_backfill` as the sources. The user pointed out that every form prints its edition at the bottom of each page. The importer's reader was silently broken (it called the `pdf-parse` v1 API against v2, so no template ever had `editionDateSource = "pdf"`). Fixed: footer-only extraction for both shapes (`Form I-131 Edition 01/20/25 Page 1 of 14` and the older `Form G-28 09/17/18 Page 1 of 4`); the most frequent date wins, a tie is ambiguous; OMB `Expires` and EOIR `Rev.`/`Exp.` are never read. Naming format unchanged: version `yyyy-mm-dd` and stored file `<form>_<yyyy-mm-dd>.pdf`.

**C4. Data corrections made with the user's permission** (dry run first, byte-verified copy, old file kept, idempotent): `scripts/correctEditionFromPdfFooter.js` - I-589 2026-09-15 -> 2026-07-28, I-131 2026-09-18 -> 2025-01-20 (a retired same-edition manual upload only had its label moved aside to `2025-01-20-manual-upload`), G-28 2026-09-22 -> 2018-09-17; `scripts/fillMissingEditionDatesFromPdfFooter.js` - 19 missing edition dates filled (G-1145, G-1256, G-1650 and G-28I deliberately left undated at the user's request). Findings left open: the AR-11 and G-28 review rows hold the wrong PDF (EOIR-29); the retired I-485 row's date differs from its footer.

**C5. The 12-hour check belongs to this subsystem.** The existing `USCISCatalogSyncJob` (every 12 h, 10 min after start) already lists every form on uscis.gov, compares edition dates, leaves unchanged forms alone and drives changed/new ones through the automatic pipeline (fetch with retry -> qpdf normalise / XFA removal -> import -> carry the mapping forward or apply authored rules -> certification -> promote only if everything passes). It now calls `EditionPolicyScheduler.runScheduledEditionChecks()` afterwards, which runs the same automatic check for every edition on file; the job has no acceptance logic of its own. Both pipeline-triggered and scheduled checks run only with `FORM_EDITION_AUTO_EVIDENCE=true`, which is **on** in `Backend/.env` (user decision). Rev 9's "no disable switch" still holds for the gate itself: the flag only controls whether the system records decisions on its own.

**C6. Enforcement scope is "pipeline only" (user choice).** `EditionPolicyEnforcer.requireAcceptedEdition` (fail closed, throws `EditionPolicyHeldError` 409 before anything is changed, any internal error is a hold) is called at: `VersionManagementService.activate`, `uscis-form-importer.service.activateVersion`, `CaseFormEditionMigrationService.migrateCaseFormsToEdition`, `importLocalForm.js`, all 11 bootstrap seeds, `scripts/replaceFormEdition.js`. The `activateOrPromote` rescue now restores only the edition that was live before the attempt (the "most recently retired" rescue was removed). An entry-point matrix test fails if a new file makes an edition live without the gate. **Rule J (blocking ready_for_pdf / locked / FINAL copy / finalize / record filing for non-accepted editions) is not enforced.** Grandfathering is unchanged: live editions keep serving.

**C7. Gemini.** The 12-hour pipeline is pure code; Gemini is used only for document intelligence (passports, resumes). Phase 4 (Gemini mapping behind `FORM_AI_MAPPING`, golden set, accuracy gate) is unchanged in the plan and **has not been built**; the user restated that they want Gemini used for autofill/mapping of changed forms, so it remains the next major item once approved.

**C8. Database rule.** Initially "do not write to the real database; at most one test case". Lifted by the user the same day: "you can write in the database, just do not create a case." Writes so far: the three form-edition collections and their unique indexes, edition corrections on form templates and stored files, `FORM_EDITION_AUTO_EVIDENCE`. Never create cases, users or companies as test data. The form-edition collections are append-only by design.

## Context
The code-only pipeline (fetch -> normalize -> import -> map -> certify -> promote) repeatedly stops short of production-ready. I-131 proved it: a deterministic rich-text bug in the certification probe left a fully imported edition in `review` and nothing re-drove it. The goal is not "every form imports"; it is: every field maps to the right canonical path and PARTY, the right client's answers reach the right PDF widget, failures recover across restarts, and a new edition never breaks live templates or cases, nor reaches cases when USCIS does not accept it.
Governing principle: **never trade correctness for apparent completion.** If a PDF is unavailable, a field cannot be mapped reliably, a repair fails validation, or an edition is not accepted by USCIS, the result is a visible UNRESOLVED/HELD state - never an auto-promoted form that merely looks ready.
Four qualities, built and reported separately: import reliability / mapping accuracy / autofill correctness / operational reliability. Technical success (imported) is displayed separately from business readiness (required fields mapped, questionnaire coverage, conditions supported).

## Approved decisions
1. **Degraded release:** only an explicit allow-list of NON-critical checks, only after all critical gates pass; failed checks, limits and authorizer recorded. The exact override boundary is the table in Rule C - an override can never touch critical failures or a non-accepted edition.
2. **Edition policy (approved):** per-form USCIS edition-acceptance policy. Automatic promotion stays the default when the edition is verified and no hold applies. NEVER automatically promote, or migrate cases to, an edition USCIS does not accept. Material field changes or unresolved mappings still need approval (existing `acknowledge` flow).
3. **Gemini tiering (approved):** auto-use only unambiguous, low-risk TEXT mappings after validation. Sensitive/complex fields (address blocks, checkbox/radio/dropdown, conditional, repeating, SSN/A-number, other-party fields) stay `needs_review` unless corroborated by trusted sibling mappings or verified fixtures.
4. **Scope:** persistent recovery + Gemini mapping in one program, delivered in phases; Gemini only after Phases 2-3, behind a flag, shadow first.
5. **Local MongoDB (NOT authorized):** do not create `immigrationcrm_test` or touch any DB until the user approves after ownership/isolation is verified. See "Unresolved prerequisites".
6. **Frozen case statuses (approved, round 4):** adopt the UNION of all eight statuses used by the three existing frozen lists, defined once in a single shared module; every automatic migration path uses it. Frozen cases stay on their existing edition and are REPORTED for admin reconciliation, never silently migrated. Statuses were verified against `CaseForm.status` first (see Rule G).
7. **Edition-acceptance evidence (approved, round 4; roles corrected round 5):** EXACTLY the `admin` and `team_lead` roles (not `super_admin` unless separately approved) may submit/update evidence to resolve an acceptance hold. Official USCIS source URL + edition + acceptance/effective/rejection dates (where applicable) are required; the SYSTEM fetches and snapshots the source and re-runs the gate; a typed claim never establishes acceptance; every submission, snapshot and verification decision is audited (user + timestamp). Neither role can override an explicitly non-accepted edition or a critical release failure. Supplying evidence is not overriding a check; approval of material mapping changes stays a separate workflow.
8. **Pre-image retention (approved, round 4):** 90 days initial, subject to organizational retention requirements; separate collection tied to case + migration job; restricted access; never expired for unresolved migrations or active investigations; cleanup and recovery documented (Rule G).
9. **Initial edition policy (approved, round 6): evidence-first per form, then refresh.** USCIS acceptance is never inferred from silence (an edition on an official page, an explicit statement of acceptance, and the absence of a rejection notice are three different claims). Admin/Team Lead verify each form's official source once; thereafter the system may refresh and AUTO-ACCEPT a later edition only when the verified source satisfies the single `FilingEligibilityStatement` predicate (Rule D; constant FALSE until real-notice fixtures validate a pattern, so machine auto-acceptance is OFF; an effective date alone is NOT acceptance; amended rounds 7-9); anything unclear goes to human review / stays held.
10. **No policy-approved edition (approved, round 6):** legal acceptance outranks "one active edition at all times". Block form acquisition/generation for that form only (case creation is NOT blocked: the affected CaseForm stays pending with no PDF generation), preserve existing case references, alert admins, report "no policy-approved edition available". Never reactivate or promote an edition that fails the policy gate to restore the invariant.
11. **Admin "Fetch from USCIS" (approved, round 6):** enqueue + status polling (job id returned immediately; Admin UI shows progress). Heavy work never runs on the API main thread.
12. **Live I-131 (approved, round 6):** left untouched; flagged by the pre-rollout report for review (see Findings). No rollback unless separately approved later.
13. **Live editions are grandfathered (approved, round 7):** editions live before the gate ships stay TECHNICALLY AVAILABLE (existing references, editing, review, "ATTORNEY REVIEW" PDFs) but are NOT filing-eligible (decision 17 / Rule J) and cannot be promoted/re-activated/migrated-to until a verified decision exists; only an explicit `not_accepted` or no usable edition triggers blocking (Rule D, invariant in Phase 3).
14. **Worker isolation (approved, round 7):** a separately supervised PM2 process (own memory limit, crash isolation, lockstep deploy, job `schemaVersion`); requires a deploy-workflow change and its own production approval; no inline fallback ever.
15. **Performance budgets (approved, round 7):** proposed tolerances (p50 <= +5%, p95 <= +10%, event-loop p99 <= +10 ms / max <= +50 ms during a pipeline job) with a defined baseline protocol; the user approves the FINAL numbers after the baseline and before any comparison; zero-added-hot-path-DB-calls is a separate hard check.
16. **Release 0b evidence resolution (approved, round 7):** minimal Admin screen + verbatim-quote review (the system verifies the quote appears in its own fetched snapshot, plus artifact consistency, and the reviewer explicitly confirms the decision); what is resolvable and what stays held in 0b is defined in Rule D.
17. **Grandfathering is not filing eligibility (approved, round 9):** grandfathered editions are technically available only (existing references, editing, review, "ATTORNEY REVIEW" PDFs); filing-ready actions - move to `ready_for_pdf`/`locked`, generate the FINAL/clean filing copy, finalize a package, record a filing - require a verified filing-eligibility decision; `not_accepted` blocks them outright (Rule J).
18. **Decision responsibility (approved, round 9):** `admin`/`team_lead` decide; for an `accepted` decision the decider differs from the submitter (four-eyes).
19. **Gemini accuracy gate (approved, round 9):** pre-approved numbers and a named independent domain reviewer - see Phase 4 (zero critical role/integrity failures; precision >= 99% on >= 300 verified auto-used text mappings; >= 3 forms per family with a held-out form; >= 25 verified fields per widget type). The baseline informs but never defines success.
20. **Audit retention (approved, round 9):** permanent append-only decision/source/audit-event collections (no TTL) + a secondary `AuditLog` copy.

**D. Edition policy - unambiguous two-collection data model, resistant to stale information.**
- **`FormEditionDecision` = exactly ONE row per `{formCode, editionIdentifier}` (unique index).** Fields: `decision` (accepted | not_accepted | held | grandfathered), `status` (verified | unverified | stale | conflicting), `effectiveDate` (when THIS edition becomes usable/required, if stated), `rejectionDate` and `graceUntil` (when THIS edition stops being accepted, if stated - these live on the OLD edition's own row, populated from evidence about the replacing edition), `evidenceRefs[]`, `decidedBy` (human id or `pipeline:official_source`), `decidedAt`, `reviewBy` (expiry), `holdReason`. There is NO `acceptedEditionDates[]` array. The gate looks up the decision by the EXACT edition identifier; a decision can only cite evidence whose snapshot names that same edition identifier, so a decision for one edition can never authorize another.
- **`FormEditionSource` (separate collection) = immutable evidence snapshots:** `sourceUrl`, final URL after validated redirects, `fetchedAt`, HTTP status, `snapshotHash` (sha256 of the extracted text), the stored extracted text, `fetchedBy`, freshness (`fetchedAt` vs the staleness window). One snapshot may be referenced by several decision rows (e.g. a notice that accepts the new edition AND sets the old edition's rejection date); each row owns its own conclusion, evidence, freshness and expiry.
- **Three different things, never conflated:** (1) the **edition date printed on the PDF** (identifies the edition); (2) the edition's **effective date** (when it may/must be used) - an effective date alone is NOT acceptance; (3) **USCIS's explicit statement** of which edition is accepted and, where relevant, when an older edition stops being accepted. A source authorizes `accepted` only when its verified content establishes that specific decision for that specific edition; an effective date is interpreted as acceptance only where the authoritative source explicitly states that relationship.
- **ONE automatic-acceptance predicate, used identically in the plan, code, tests and Admin UI: `FilingEligibilityStatement(edition)`.** Three facts are kept separate (table below). The predicate is TRUE only when ALL hold: (1) the source is official, fresh and consistent with the artifact (host/https/validated redirects, page = PDF = template edition, PDF checksum); (2) the snapshot names the SPECIFIC edition identifier; (3) the snapshot text matches a **fixture-validated pattern** that explicitly states filing eligibility for that edition (e.g. "USCIS accepts/will accept edition X for filing [from date D]", or "edition Y is not accepted after D; edition X is required"). An edition date, an effective date, page structure or silence are NEVER inputs. **Until real USCIS notice fixtures validate a pattern the predicate is constant FALSE: machine auto-acceptance is OFF and every acceptance is a human decision; ambiguous cases stay held for human review.** The phrase "explicit acceptance/effective-date statement" is retired everywhere.

| Fact | What it establishes | Enough to authorize acceptance? |
|---|---|---|
| PDF edition identifier/date | Which edition the downloaded artifact represents | No |
| Effective date | When a stated rule or edition takes effect | Not by itself |
| Explicit acceptance or filing-eligibility statement | What the verified official source says about use of that edition | Only when it satisfies the predicate above (fixture-validated) |

- **What the system can verify automatically vs what needs a human:** AUTOMATIC = source authenticity (allow-listed host, https, validated redirects), source-to-artifact consistency (page edition = PDF-extracted edition = template `editionDate`; re-downloaded official PDF sha256 = imported PDF), snapshot integrity and freshness, structural extraction of dates. A fetched page plus matching checksums prove consistency, NOT a legal conclusion. HUMAN = the legal conclusion (accepted / not accepted / grace), made by `admin`/`team_lead` and bound to verifiable source text (verbatim-quote review below). Consequence (accepted): USCIS pages rarely state acceptance explicitly, so later editions will need human review almost every time until fixtures from real notices prove a reliable explicit-statement pattern; decision 9's auto-accept applies ONLY where such a pattern is proven.
- **Grandfathering (decision 13):** editions that are live before the gate ships get `decision: grandfathered`: they stay technically available (existing references, editing, review, "ATTORNEY REVIEW" PDFs) but are NOT filing-eligible (Rule J) and can never be promoted, re-activated or migrated-to until a verified decision exists; only an explicit `not_accepted` or the absence of any usable edition triggers blocking.
Rules:
- **Three different identifiers, never conflated (the gate checks each for its own purpose):** (1) **Form PDF checksum** - identifies the exact PDF imported/under review; before promotion the official PDF at the page's link is re-downloaded and its sha256 compared with the imported artifact (a mismatch for the same edition = conflicting => held). (2) **Official-source snapshot hash** - identifies the fetched evidence (page/alert text) used for the policy decision; it is stored and audited, never compared to the PDF checksum. (3) **Edition identifier/date** - which edition the evidence refers to. The gate verifies that the authoritative source supports the SPECIFIC edition under review and that the page edition, the edition extracted from the PDF and the template `editionDate` AGREE; any disagreement => `conflicting` => held. **Only edition dates from an official source (page or PDF) are trusted**: `editionDate` values with `importMetadata.editionDateSource: version_backfill` (copied from an import-date-shaped `version`) are UNTRUSTED. `version` is never the edition (live data: I-765 version 2026-09-22 but edition 2025-08-21; I-864 version 2026-09-22 but edition 2026-08-24).
- **Evidence-first (decision 9). A missing policy record NEVER authorizes anything: no record => held.** Auto-promotion AND auto case-migration require, for the edition in question, `status: verified`, not past `reviewBy`, `decision: accepted`, no hold, and a fresh official-source re-fetch performed just before promotion. The INITIAL record for a form is created only through the evidence workflow below (admin/team_lead submission verified by the system). Once a form has a verified policy, a scheduled refresh may MAINTAIN it only when the source can be reliably verified (same official source still parses and states the same facts); it may AUTO-ACCEPT a LATER edition only when that source satisfies the single `FilingEligibilityStatement` predicate defined above (constant FALSE until real-notice fixtures validate a pattern, so machine auto-acceptance is OFF) - the absence of a rejection notice is NOT acceptance and an effective date alone is NOT acceptance; anything else goes to human review. The resulting decision is PERSISTED (`verifiedBy: pipeline:official_source`, snapshot hash, `verifiedAt`, `reviewBy`) before the gate is re-run and may return `allowed`; if the fetch, snapshot write or persistence fails, or evidence is unavailable, stale, ambiguous, conflicting or unverifiable, the result is `held`. No default/auto-accept decision type, no disable switch. Currently-active editions stay technically available for existing cases but are not filing-eligible until a verified decision exists (Rule J) (the gate runs at promotion/migration/re-activation time, it does not deactivate live editions).
- Stale, conflicting or unverifiable information => HOLD (never promote, never migrate) until resolved through the evidence workflow below. A parser alone never establishes legal acceptance.
- The notice-phrase scanner ("will not accept", "continue to accept", "court order", "grace period", "rejected") is an EARLY-WARNING only: it can ADD a hold and alert; it can never mark an edition accepted. A hold is lifted only through the evidence workflow.
- **Evidence workflow (resolving a hold).** **Approved roles are EXACTLY `admin` and `team_lead`.** `super_admin` is NOT included unless the user separately approves it; `case_manager` and every other role may not submit or update evidence. Implementation rule (verified in `rbac.service`): the endpoint uses the exact-match `authorizeRoles("admin","team_lead")` plus a role re-check inside the service, and NEVER `authorizePermissions` - `hasPermission` returns true for every `super_admin`, for users holding `"*"`/`resource:*`, and honors runtime-editable `roles.permissionOverrides`, any of which would break the exact-role rule. The same allow-list is enforced in the API route guard, in the Admin UI (control hidden/disabled for all other roles) and in the documentation, and is covered by authorization tests (admin and team_lead allowed; super_admin, case_manager, attorney, paralegal, finance, HR, client all denied). Required inputs: official USCIS source URL, form edition identifier/date, acceptance/effective/rejection/grace dates where applicable, and the **verbatim quote** - the exact sentence(s) from the official source that support the decision being recorded. The submission is a CLAIM: the SYSTEM fetches the URL with the dedicated redirect-safe fetcher (Rule H), stores an immutable snapshot in `FormEditionSource`, and verifies: (a) the source is official and fresh; (b) the **quote appears verbatim in the system's own snapshot text**; (c) the specific edition identifier appears in the snapshot; (d) page/PDF/template edition and PDF checksum are consistent; (e) the claimed dates match the quoted text. Only then is the decision row written and the gate RE-RUN. If any check fails or the snapshot is ambiguous the result is `conflicting`/`unverifiable` and the hold stays. A typed claim without a verifiable quote can never set `accepted`; the legal interpretation stays with the human reviewer but is bound to source text the system itself verified. **A matching quote proves only that the text exists in the official snapshot - NOT that the recorded legal conclusion is correct.** Therefore the `admin`/`team_lead` reviewer must EXPLICITLY CONFIRM the decision (an affirmative confirmation step stating the decision - accepted / not accepted / grace until D - for the named edition, shown next to the quote and the verification results), and the audit trail records: reviewer id and role, timestamp, edition, the decision, the verbatim quote, the snapshot hash, the verification results and the gate result. No decision is written without that confirmation. **Machine auto-acceptance is OFF: it is not implemented in Release 0a/0b or Phases 0-1 and stays off until real USCIS notice fixtures validate the rule; enabling it is a separate, explicitly approved code change (not a runtime flag).** Anything ambiguous stays held.
- **Release 0b scope (usable on day one, without accepting unverifiable claims):** RESOLVABLE in 0b = uscis.gov HTTPS sources whose snapshot contains the reviewer's verbatim quote and the edition identifier, with consistent artifacts, submitted by `admin`/`team_lead` through the 0b Admin screen. STAYS HELD until later phases = non-uscis.gov sources; text that cannot be fetched or extracted; claims that conflict with page/PDF/template; any explicitly `not_accepted` edition; court orders not captured on a USCIS page; and ALL machine auto-acceptance (needs fixtures, Phase 2). Audit (immutable) for every submission, snapshot and verification decision: submitting user, role, timestamp, URL, snapshot hash, claimed vs corroborated values, gate result. Neither role can mark an explicitly `not_accepted` edition accepted or release a critical failure. Corroboration rules (what text proves acceptance) need fixtures built from real USCIS notices before they ship; until then anything with notice language stays held.
- **Responsibilities, separation of duties and audit (decisions 18, 20).** Submitting evidence and deciding filing eligibility are distinct steps. Exactly `admin` and `team_lead` may do either (no `super_admin`), but for an `accepted` decision the DECIDER MUST DIFFER FROM THE SUBMITTER (four-eyes, enforced in the service and covered by tests); `not_accepted` / `held` decisions, which only restrict, may be recorded by one person. The system records the organization's decision; it does not give legal advice. SIX separate immutable events, linked by an `evidenceCaseId`: (1) `EVIDENCE_SUBMITTED` - user, role, URL, claimed edition/dates, quote; (2) `SOURCE_FETCHED` - final URL, validated redirect chain, HTTP status, snapshot hash, fetchedAt; (3) `VERIFICATION_COMPLETED` - quote found verbatim?, edition identifier found?, page/PDF/template consistency, checksum, per-check pass/fail; (4) `DECISION_RECORDED` - decider id/role, decision, effective/rejection/grace dates, quote, rationale, explicit-confirmation flag, edition; (5) `GATE_RECALCULATED` - inputs, result, reasons, decision-row version; (6) `OUTCOME_RECORDED` - promoted / held / blocked, job id, entry point, actor. **Storage:** the authoritative record is the permanent append-only `FormEditionSource`, `FormEditionDecision` and a dedicated append-only `FormEditionAuditEvent` collection with NO TTL (retention set later by organizational requirements); `AuditLog` (immutable, but with a 2-year TTL) holds only a secondary copy.
- Case migration (`migrateCaseFormsToEdition`) refuses a target edition the policy does not accept; frozen forms stay on their edition.
- **Phase 0 interface:** `EditionPolicyGate.check(formCode, editionIdentifier) -> { allowed, decision, status, reasons }` (lookup by the exact edition; `grandfathered` => serve-only, never promote/re-activate/migrate-to) with the conservative rules above, called by EVERY activation path (`activateOrPromote`, `VersionManagementService.activate`, lifecycle/import activate routes, rollback, `USCIS_ONDEMAND_AUTOACTIVATE`, scripts, scheduled jobs, autopilot, `acquireForCase` and `migrateCaseFormsToEdition`) from the first release, fail-closed (Rule C). **J. Technical availability vs filing eligibility (decision 17).** A grandfathered edition is TECHNICALLY AVAILABLE only: it preserves existing references, editing and review, and it NEVER authorizes a newly generated filing-ready PDF while acceptance is unknown. Filing eligibility is a separate, per-edition determination that respects effective/rejection/grace dates (an older edition can be eligible until `graceUntil`). Verified: the system already separates review copies from filing copies - `PDFGenerationService` watermarks "ATTORNEY REVIEW" by default and "FINAL" when the form is `locked`/`ready_for_pdf`; `PDFRenderer` has a clean, watermark-free filing-copy path; `PetitionAssemblyService` finalizes "clean, no watermark" packages and records filing - so the rule attaches to existing transitions, no redesign.
| Action | Requirement |
|---|---|
| Edit/review a form; view existing documents; generate the "ATTORNEY REVIEW" watermarked PDF | Allowed for grandfathered/unknown editions (a prominent warning banner shows when acceptance is unverified or the edition is `not_accepted`) |
| Move a form to `ready_for_pdf` (`interactive-form-review.service.js` ~:821) or `locked` (~:864, `PDFGenerationService` ~:339) | Requires a verified filing-eligibility decision for that edition (eligible, within any `graceUntil`/rejection date) |
| Generate the "FINAL" copy or the clean filing copy (`PDFGenerationService`, `PDFRenderer` filing-copy path) | Same |
| Finalize a package / record filing (`PetitionAssemblyService`) | Same |
| Any of the four filing-ready rows when the edition is `not_accepted`, or acceptance is `held`/`grandfathered`/unknown | BLOCKED with a clear message ("edition acceptance not verified - ask an admin/team lead"); `not_accepted` is blocked outright, no override; the others are resolved only through the evidence workflow |
- Already frozen cases (finalized, filed, locked, ...) are not re-evaluated automatically; they are reported (Rule G), with PRIORITY when the edition is `not_accepted`.
- **Lookup placement:** only at those four mutation transitions (never autofill, form load, case read or case creation), through a short-TTL in-process cache, fail closed on error - the zero-added-hot-path-DB-calls hard requirement (Rule F) is unaffected. These transitions join the entry-point matrix test.

Mitigation: the Release 0a report counts open case forms per form, edition and status (esp. `approved`/`under_review` near `ready_for_pdf`) so evidence is submitted first for the forms with the most open work; the same minimal Admin screen resolves them; deadlines/grace periods are recorded in `graceUntil`.

Visible to admins in FormGovernance and counted in the outcome email; never silently migrated.
- **Answer record** = every persisted per-field datum: value (`filledData`/`fieldValues`/`manualOverrides`), `fieldValueProvenance`, `sourceAttribution`/verification status, field review status, override metadata (who/when). (Verify-first: confirm these are keyed by field id; the current service migrates only the three value bags, so verification/review/provenance could be lost on a rename and the next autofill could overwrite a verified value.)
- **Dispositions** - every old record ends in exactly one: **preserved** (same value + metadata under the new key), **archived-with-reason** (no counterpart | inapplicable by the new edition's condition | equal-value collision merge), **unresolved** (conflicting values colliding on one target, or a verified/manual-override value with no valid counterpart). Any unresolved record BLOCKS that case's migration: it stays on its old edition and is reported; other cases proceed.
- **Collisions** (two old keys -> one new target) are detected before writing; different values => unresolved, never a silent overwrite.
- **Provenance classification (explicit rule, including missing/ambiguous provenance):** (1) PROVEN default/autofill value (provenance source default/autofill/canonical-derived, or equal to the template default with no override) => may be classified a non-answer under the documented category rules; (2) PROVEN user-entered, manually overridden, questionnaire-answered or verified value => PRESERVED (a user-sourced `false` is a real answer, preserved and restored; replaces the current `isBlank` treatment of `false`); (3) UNKNOWN or missing provenance on a potentially meaningful value (non-blank and not equal to a template default) => NEVER silently discarded: preserved when it maps cleanly (flagged `provenance_unknown`), `unresolved` if it collides with another source, and archived-with-reason (retained and visible in `editionMigrations[]`) if it has no counterpart; unknown-provenance blank values are non-answers. Applies especially to legacy records predating reliable provenance. Current live data: all 37 case forms have non-empty `fieldValueProvenance` and `sourceAttribution`, 0 have `manualOverrides`; document-level presence says nothing about per-field coverage, so the migration dry-run report MEASURES per-field provenance coverage before any migration.
- **Pre-image + read-back verification (replaces `carried + archived == total`, which is circular by construction).** Per case: (1) store a full pre-image (all answer records + status + `formVersionLock`) in a separate collection with a checksum; (2) write migration state on the CaseForm (`migrationState{jobId, snapshotId, step}`, additive, small); (3) migrate; (4) autofill + restore; (5) RELOAD the CaseForm from the database and verify against the pre-image dispositions (values, provenance, verification/review status, override metadata; user-sourced values not blanked or altered; verified values intact); (6) on any mismatch follow the SAFE RECOVERY rule below (restore only when no newer edits exist, otherwise hold for audited reconciliation) and report it; (7) mark `completed`. Every step saves with a compare-and-set on the case form's version/`updatedAt` (needs a small additive `CaseForm` concurrency setting - verify first); a concurrent user edit causes a re-read and re-plan, never an overwrite.
- **Safe recovery without overwriting newer edits (applies to failed verification, the reconciliation sweeper and any manual restore).** At the `saved` and `autofilled` steps store an `expectedIntermediateChecksum` (hash over the canonical answer records + status/lock/template pointers) in `migrationState`. Before ANY restore: (a) verify the pre-image checksum (mismatch => refuse); (b) compute the current case's state and compare it with the expected intermediate state for the recorded step; (c) identify answer records changed after the snapshot (field-level diff, with who/when from provenance `revision`/`overriddenAt`/`overriddenBy`, audit history and `updatedAt` where recorded - attribution is best-effort). If the current state equals the expected intermediate state (only the migration's own changes) => restore automatically. If ANY newer edit exists => DO NOT overwrite: set `migrationState.step = reconciliation_required`, keep the case held (not restored, not re-migrated, banner shown; the case stays editable), PRESERVE the pre-image with no expiry, alert admins and report the conflict (case, fields changed since the snapshot, expected vs actual, who/when where known). Resolution is only through an audited admin reconciliation tool (per field: keep current | use pre-image | merge) after which the case is re-verified. Recovery is idempotent: restoring an already-restored case (current == pre-image checksum) is a no-op, and recorded reconciliation decisions can be re-applied safely.
- **Per-case completion marker + reconciliation.** `migrationState.step` advances snapshotted -> saved -> autofilled -> verified -> completed. The reconciliation sweeper (start-up + every tick) selects cases with an incomplete step (the current selection query only finds cases still on an OLD template, so a crash after the new edition is saved but before autofill/verification would be missed forever) and resumes from the recorded step; a failed verification follows the safe-recovery rule (restore only with no newer edits, otherwise `reconciliation_required`). Idempotent; per-case isolation; the job never aborts the batch.
- **Pre-image store** (`CaseFormMigrationSnapshot`, separate collection): fields `caseFormId`, `caseId`, `migrationJobId`, `formCode`, `fromTemplateId`, `toTemplateId`, `preImage`, `checksum`, `createdAt`, `state` (active|released|purged), `legalHold`, `expiresAt`. Retention: `expiresAt = verified-completion + 90 days` (initial, subject to organizational retention requirements); `expiresAt` is NOT set (no TTL) for unresolved/failed migrations, active investigations or `legalHold`, so a TTL index never removes them. Access: excluded from all normal case APIs/populates; read/restore only through an audited route restricted to roles confirmed before Phase 3 (assumption: `admin` only; no implicit `super_admin` or `team_lead`); contains client data so same protection as CaseForm, never logged. Cleanup: TTL index on `expiresAt` (+ a scheduled report of purge counts to the audit log); recovery: audited `restoreCaseFormFromPreImage(snapshotId)` with dry-run, checksum verification, and the safe-recovery rule (no automatic restore over newer user edits). Snapshots in `reconciliation_required` are preserved without expiry. Size: stored outside the CaseForm to avoid growing case documents.

If none exists, no unapproved edition is activated; acquisition and PDF generation for that form are blocked, existing references are preserved, and the invariant is reported as unsatisfied." Clarifications: (i) it is a POST-RECONCILIATION steady-state rule - while a promotion is in flight two editions may be active briefly (activate-new-then-retire-old), but never zero when the old edition is still policy-approved; (ii) when two editions are both approved (e.g. during a grace period) the NEWEST approved edition is the active one; (iii) `grandfathered` editions (live before the gate shipped) count as technically available for this rule (existing references, editing, review) but are NOT filing-eligible (Rule J), so shipping the gate does not by itself shut down any form - only an explicit `not_accepted` decision, or the absence of any usable edition, triggers blocking. **If no policy-approved edition can be restored:** block form acquisition/generation for that form only (case creation is NOT blocked; affected CaseForms stay `pending`, no PDF generation), preserve existing case references, alert admins, and report "no policy-approved edition available" - the invariant is reported as UNSATISFIED, never claimed as satisfied.
- **Case migration recovery:** per Rule G - per-case completion marker and reconciliation resume any case interrupted after the new edition was saved (before autofill or verification); a failed read-back verification restores the case from its pre-image only when no newer edits exist, otherwise the case is held for audited admin reconciliation with the pre-image preserved. Invariants: no duplicated CaseForm; every old answer record has exactly one disposition (preserved | archived-with-reason | unresolved-blocking); verified/manual values intact; frozen forms untouched and reported; a case is never left half-migrated unrecoverably (each case is a single-document save plus a recoverable state machine).
- Rollback: restore prior template + mapping from retained versions, only if the prior edition passes the policy gate (else held/blocked as above), re-certify, invalidate cache; cases are NOT moved back - affected cases are listed for admin reconciliation. Backup JSON records template/mapping-version ids + checksums.

2. **Findings (verified):** retries are in-process only; no durable job/resume; failure causes exist only in return values; release gate is split across entry points; **non-active (`needs_review`) edges are projected to autofill by BOTH `FormMappingService.applyMappingGraph` (read-time projection; called by `AutoFillService`, `interactive-form-review.service`, `uscis-form.service`) and `MappingGraphService.graphToFieldMappings` (persist-time projection)** - 0 of 45 live active mapping versions contain a non-active edge today, so filtering both changes no live behavior; autofill also reads legacy `field.mapping{}` (0 live fields) and `defaultValue` (3,669 live fields across 29 active templates: 3,095 unchecked-checkbox `"false"`, 225 empty dropdown values, barcode tokens such as `I-129F|01/20/25|1`, and a few constants; no party-looking text defaults found - to be fully classified and snapshotted before any restriction); lifecycle and import activate routes skip cache invalidation; the frozen-status rule is defined in THREE places with different values (`CaseFormEditionMigrationService` 5, `applyPartyMappingsToExistingCases.js` 5, `replaceFormEdition.js` 7) and `receipt_received` is not a valid `CaseForm.status`; impact text says "new_cases_only" while promotion migrates open cases; the migration check `carried + archived == total` is circular by construction, colliding targets overwrite silently, verification/review/provenance metadata is not migrated, `false` is treated as blank, and a crash after saving the new edition but before autofill is never resumed; `verifyFormImportEndToEnd.js --cleanup` deletes all templates of a form code; `fill_roundtrip` writes the same probe everywhere and skips checkbox/radio/dropdown.
3. **Corrections made during review:** the projections are `FormMappingService.applyMappingGraph` (read-time) and `MappingGraphService.graphToFieldMappings` (persist-time) - not `applyGraphToTemplate` alone; the invented `FORM_EDITION_POLICY_ENFORCE` flag was removed (safety checks have no disable switch); persistVersion is a chokepoint for graph versions only; test DB feasibility; `deleteFormFromCatalog` is not a rollback hazard; cross-instance cache downgraded; "filing requires the newest edition" is not universal (per-form USCIS rules).
4. **Decisions:** developer email on every success/failure/held outcome (reuses `email.service`; deduped per edition/state/stage/error); degraded-release policy; per-form edition policy with conservative auto-hold; Gemini low-risk-text-only auto-use; single MappingPolicy at `persistVersion`; no automatic case move-back; no new artifact store; local test DB not yet authorized.
4f. **Round 9 additions:** (a) grandfathered editions are technically available only; filing-ready actions (ready_for_pdf/locked, FINAL/clean copy, finalize, record filing) require a verified eligibility decision and `not_accepted` blocks outright; (b) one `FilingEligibilityStatement` predicate, constant false until fixture-validated; (c) pre-approved Gemini accuracy gate (zero critical role/integrity failures; precision >= 99% on >= 300 verified auto-used mappings; >= 3 forms per family with a held-out form; >= 25 verified fields per widget type) against an independently reviewed golden set; (d) decider differs from submitter for `accepted`; six separate audit events stored in permanent no-TTL collections (the existing `AuditLog` expires after 2 years, so it is a secondary copy only).
4e. **Round 8 additions:** performance acceptance is stated against approved baseline tolerances with zero added hot-path DB calls as a separate hard requirement; legal decisions require explicit reviewer confirmation recorded with the verbatim quote (a matching quote proves only that the text exists in the snapshot) and machine auto-acceptance is not implemented until real fixtures validate it; Release 0b is split (0b-1 evidence path without enforcement, readiness gate proven end to end, 0b-2 enforcement separately approved); plan approval authorizes only Release 0a.
4d. **Round 7 additions:** (a) single invariant wording with a grandfather clause (live editions are technically available but not filing-eligible until a verified decision exists - Rule J) and legal-safety priority; (b) edition-policy data model = one decision row per form+edition plus immutable source snapshots (no `acceptedEditionDates[]`); (c) precise acceptance definitions - PDF edition date vs effective date vs USCIS's explicit acceptance statement; automatic verification covers authenticity/consistency, a human makes the legal conclusion bound to a verbatim quote the system verifies in its own snapshot; (d) Release 0b ships a minimal Admin evidence screen with the gate; resolvable vs held-in-0b cases are defined; (e) reproducible performance budgets (baseline protocol; proposed tolerances approved after baseline) and a separate zero-added-hot-path-DB-call check; (f) worker = separately supervised PM2 process; (g) Phase 0 is an interim fail-closed layer with exact checks per phase (certification on record required; none => held); (h) redirect-safe `OfficialSourceFetcher` (both existing fetchers validate only the first URL and follow redirects; read-only checks show USCIS URLs tested do not leave uscis.gov; full crawl in Release 0a); (i) approvals are per phase and completion reports + regression results gate the next phase.
4c. **Round 6 additions:** (a) evidence-first edition policy - acceptance is never inferred from silence; initial policy per form via verified evidence, machine auto-acceptance only via the single `FilingEligibilityStatement` predicate (constant false until fixtures validate it); (b) three separate identifiers (PDF checksum, official-source snapshot hash, edition identifier/date) with page/PDF/template edition agreement, and `version_backfill` edition dates untrusted (live I-131 edition 2026-09-18 came from `version_backfill`; official page lists 01/20/25); (c) heavy work never on the API thread - measured I-131 5.5s/98ms and I-129 10.8s/244ms main-thread blocking per load+save; worker unavailable => queued/held + alert; admin Fetch becomes enqueue + polling; (d) legal acceptance outranks the one-active-edition invariant (existing rescue step reactivates a retired edition with no gate and is rerouted through it; with no approved edition block form acquisition/generation for that form only); (e) unknown-provenance migration rule and canonical-state equality instead of byte-equality; (f) release sequence 0a (read-only report) then 0b (gate + minimal evidence intake together).
4b. **Safety boundaries (round 4):** edition-policy gate and ReleaseGate fail closed with no disable switch (gate exception, stale/unavailable policy or unverifiable acceptance => hold promotion and migration; read-only pre-rollout report reviewed first). Override boundary: non-critical failures => documented degraded release only; material mapping changes => separate approval workflow; critical failures and explicitly non-accepted editions => never overridable; stale/conflicting/unverifiable acceptance => hold until authoritative evidence. Exactly `admin` and `team_lead` (not `super_admin` unless separately approved; exact-role guard, never a permission-based guard) may SUBMIT evidence (official uscis.gov URL + edition + dates); a missing policy record never authorizes promotion - the pipeline may establish one only from a verified fresh official fetch whose decision is persisted first, and any unavailable/stale/ambiguous/conflicting/unverifiable evidence leaves promotion and migration held, with no disable switch; the system fetches and snapshots the source and re-runs the gate; a typed claim never establishes acceptance; all submissions/snapshots/decisions audited. **Worker promotion rule:** the Phase 1 worker's promote stage calls the existing guarded promotion function plus the Phase 0 policy gate, and every activation/promotion/rollback/script/scheduled/autopilot/`acquireForCase` path keeps equivalent safeguards. **Case-migration safeguards:** one shared frozen-status list (finalized, filed, approved, generated, ready_for_pdf, locked, receipt_received, archived, plus `isLocked`) - frozen cases stay on their edition and are reported; pre-image in a separate collection (90 days initial, never expired while unresolved/under investigation, restricted audited access); database read-back verification of values, provenance, verification/review status and override metadata; collision detection; user-sourced `false` preserved; dispositions preserved / archived-with-reason / unresolved (unresolved blocks that case); per-case completion marker with reconciliation; on failed verification restore from the checksum-verified pre-image ONLY when no newer user edits exist (current state compared with the expected intermediate state), otherwise the case is held as `reconciliation_required` for audited admin reconciliation, the pre-image is preserved without expiry and the conflict is reported; recovery is idempotent.
