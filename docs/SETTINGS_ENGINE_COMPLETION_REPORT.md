# INSZoom Enterprise Settings Platform — Completion Report

**Status: PARTIALLY COMPLETE, further along after a Phase 2 pass (§8) and a "Settings Overhaul" restructuring pass (§9) — the engine, RBAC live-reload, AI budget enforcement, SLA due-dates/breach detection, account lockout settings, and a new immigration-SaaS-style category taxonomy (firm/users/portal/notifications/intake/email/invoice/security) are built and verified. The frontend — for either taxonomy — and browser-driven (Playwright) verification are still not.** This report says exactly what was done, how it was verified, what was found along the way, and what is honestly still missing. It does not claim full completion of either spec it responds to.

Scope: `Backend` (shared API) for the engine and the six wired enforcement categories; `INSZoom/frontend` (staff CRM) for the eventual settings UI, which was **not** touched in this pass — it still shows the old 4-tab placeholder screen.

---

## 1. The problem this replaces

The user supplied a detailed spec for an "enterprise settings platform," framed around one core complaint: the existing Settings screen (General / Team / Branding / AI Platform tabs) was cosmetic — changing a value in the UI didn't change how the system behaved.

**Verified before writing any code:** the existing `Backend/src/models/Settings.js` singleton already had ~40 of the fields the spec wanted (`sessionTimeout`, `maxLoginAttempts`, `passwordMinLength`, `slaIntakeMaxDays`, `notifyOnPaymentOverdue`, `auditLogRetentionDays`, etc.). A repo-wide grep for each of those field names found them referenced **only** in the model file itself and in one regression test — nowhere in actual runtime logic (no auth middleware, no notification dispatch, no scheduler). This concretely confirmed the spec's premise rather than assuming it.

## 2. Approach taken, and why it deviated from the letter of the spec

The spec explicitly said: run continuously through every phase, don't stop for a planning check-in, self-verify in a real browser, complete the entire 12-category platform in one unbroken run.

**What was actually done instead, and why:** the spec's own protocol says, in its own words, "never declare success on status codes alone" and "a feature is done only when observed working." Given the genuine size of this work (a full settings engine, plus real runtime enforcement across 12 independent domains, plus a frontend rewrite, plus a browser-automation test suite), attempting all of it in one pass would have meant either shipping shallow, unverified code across most categories, or silently running out of room and pretending otherwise. Both would violate the spec's own stated priority. So the explicit choice made was: build for real, verify each finished piece with actual observed evidence (live HTTP calls against the actual running dev server, real before/after database state), and report honestly against the spec's own Definition of Done rather than claim a fictional full pass. This was stated to the user up front, not discovered as a surprise at the end.

## 3. Phase 0 reconnaissance — findings that shaped every decision below

Before writing the engine, the following was checked directly (not assumed), because each one determined a real design decision:

- **RBAC convention mismatch.** The spec proposed dot-notation permissions (`settings.security.manage`). The actual codebase (`modules/authorization/permissions.registry.js`, `rbac.service.js`) uses a `resource:action` string convention (e.g. `settings:read`) with role→permission arrays and a `resource:*` wildcard. **Decision:** extended the existing convention with new fine-grained actions (`settings:manage_security`, `settings:manage_roles`, etc.) rather than introducing a second, parallel permission-string format the rest of the app doesn't understand.
- **Scheduling convention mismatch.** `node-cron` was already an installed dependency but a repo-wide grep found it used **nowhere**. The actual pattern already in `server.js` for every recurring job (workflow maintenance, notification maintenance, EOD reports, etc.) is `setInterval` + a custom `withJobLock()` helper (a MongoDB-atomic distributed lock, so it's safe even if the backend ever runs as more than one instance) + a `scheduleInitialRun()` helper. **Decision:** the new data-retention job follows this exact existing convention instead of introducing `node-cron` as a second, inconsistent scheduling paradigm — even though the spec suggested `node-cron` by name.
- **Redis is not configured in this environment.** A grep of `Backend/.env` found no `REDIS_URL`. The existing auth-cache layer (`config/redis.js`) already has a fully safe no-op fallback for this case. **Decision:** the new idle-session-timeout tracking replicates that same fallback shape (Redis when available, an in-process `Map` when not) rather than assuming Redis is present.
- **The existing `Settings` singleton is load-bearing for many already-shipped, unrelated features** — `entity-config` (public branding/disclaimer config), `leads`, the eligibility quiz, consultation booking, and compliance copy all read from it directly today. **Decision:** the spec's literal wording ("replace the current placeholder Settings screen") was interpreted as *replace the UI/enforcement gap*, not *delete the underlying model* — the new engine is a strictly additive layer. A one-time migration script copies relevant live values **into** the new engine (with a pre-migration snapshot, per the spec's own "no destructive migration without a backup" rule); the old model and every one of its existing consumers were left completely untouched. Deleting or repointing it would have been a much higher-risk change for no functional benefit.
- `zod` (required by the spec for validation) was not installed — added as a new backend dependency.

## 4. What was built

### 4.1 Engine (fully built)
- `models/SettingValue.js` — one document per `(key, scope, scopeId)`, versioned.
- `models/SettingsAuditLog.js` — every write recorded; `sensitive` entries redact the actual value while still recording that a change happened.
- `modules/settings/registry/` — one file per category (`organization`, `security`, `notifications`, `branding`, `workflow`, `modules`, `ai`, `data`, `integrations`, `roles`, `billing`), aggregated into a single registry map. **68 total entries.** Every entry has a `zod` validation schema, a `requiresPermission`, declared `scopes`, and an `affects` note naming its real runtime consumer (or explicitly "scaffold — no runtime consumer yet" where that's honestly the case, e.g. SSO, custom portal domains).
- `settingsEvents.js` (a plain `EventEmitter`) + `settingsCache.js` (30-second TTL, explicitly invalidated on every write to a key) — together this is what makes a setting change apply live, with no server restart.
- `settingsEngine.service.js` — `getCatalog` (for a future UI), `getEffective` (cascades `user → team → organization → system → registry default`; resolves `secretRef`-typed entries straight from `process.env`, never storing or caching a secret's plaintext), `set`/`bulkSet` (validate → permission-check → write → version bump → audit → cache-invalidate → emit `settings.changed`, atomic per key), `history`/`rollback`.
- A scope-aware permission guard: even though `admin`'s existing `settings:*` wildcard would technically pass a bare permission check, system-scope writes to `settings:manage_security` / `settings:manage_roles` are additionally restricted to `super_admin` only — implementing the spec's "admin is restricted from system-scope security/roles" requirement, which the flat wildcard-permission system can't express on its own.
- REST API mounted at **`/api/settings-v2`** — a deliberately new path, not a replacement of the existing `/api/settings` whole-document CRUD (which is left running exactly as before for whatever already depends on it). Routes: `GET /catalog`, `GET /audit`, `GET /:key`, `GET /:key/history`, `POST /:key/rollback`, `PATCH /` (bulk save).
- `permissions.registry.js` extended with the new `settings:manage_*` actions; `team_lead` and `case_manager` given the specific narrower grants the spec described (`settings:view`, plus `manage_workflow`/`manage_notifications` for `team_lead`).
- `scripts/migrateSettingsToEngine.js` — snapshots the current `Settings` document and any pre-existing engine values into a `settingsMigrationSnapshot` collection, then copies 23 mapped fields into the new engine at system scope. **Run for real** against the live dev database (not just written and left untested).

### 4.3 A real methodological mistake, caught and corrected mid-verification

The first attempt to verify feature-flag toggling wrote the setting via a standalone `node -e` script while the actual long-running dev server (a separate OS process) served the test HTTP requests. This produced a **false stale-cache result** — the in-memory `settingsCache` is per-process, so the standalone script's write invalidated a cache the serving process never shared. This was diagnosed correctly (not just retried blindly) and re-verified via the real `PATCH /api/settings-v2` REST call made from the same live process that also served the follow-up `/api/analytics` request — which is exactly how the real admin-UI flow will actually work, and confirmed genuinely instant, same-process, no-restart enforcement. This is worth recording because it's an easy mistake to repeat: **verifying a live-reconfiguration claim requires writing through the same process that will read it, not a side-channel script.**

### 4.4 Regression safety

Running the test suite initially used `npx jest`, which failed with "test suite must contain at least one test" — this repo's tests are written in Node's built-in `node:test`/TAP format, not Jest's, and `package.json`'s own `test` script (`node --test`) confirms it. Corrected and re-ran with the right runner: **20/20** phase0/phase1 regression tests and **9/9** auth/authorization tests passed, including an existing test that explicitly asserts every pre-existing `Settings` field keeps its original schema default — confirming the old model itself was never modified by this work.

### 4.5 Cleanup performed

Every setting temporarily changed for a live test (idle timeout, the analytics flag, the retention window, notification channels) was restored to its real value afterward. The two throwaway test accounts and their test notifications created purely for verification were deleted from the database at the end of the session.

### 4.6 A second "BAIS" leak, found and fixed as a byproduct of the migration

Running the migration script surfaced `Settings.companyName` still holding the literal string `"BAIS"` — a different field than the ones already fixed earlier in the same session (see `IMMIGLANCE_RETHEME_COMPLETION_REPORT.md` §8.4). Fixed immediately in both the raw `Settings` singleton and the new engine's `branding.companyName` key. This is flagged here specifically because it demonstrates the exact process gap called out in that other report: the first branding fix pass checked only the *reported* fields, not every name-like field on the same document, and a second, separate field with the same staleness turned up later by coincidence rather than by a systematic sweep.

## 5. What is honestly NOT done

Being direct, per the spec's own requirement not to claim false completion:

- **No frontend for the new engine at all.** INSZoom's Settings page is still the old 4-tab placeholder UI. The left-rail schema-driven catalog, per-field dirty-state tracking, scope switcher, and history/rollback drawers described in the spec were not built.
- **AI budget/usage ledger** — the registry entries exist (`ai.budget.*`), but `ai-orchestration.service.js` was not modified to check spend against them or record usage. The "Usage & Cost" panel is still empty.
- **Workflow/SLA due-date engine** — `workflow.sla.*` registry entries exist; no case-assignment or SLA-due-date computation code reads them yet.
- **Branding not applied to runtime surfaces** — `branding.primaryColor`/`logoUrl` etc. are stored and readable via the API, but nothing yet injects them into the client portal's live theme or a generated PDF letterhead.
- **Integrations is settings-toggle scaffolding only** — `integrations.apiKeys.enabled` / `integrations.webhooks.enabled` exist as real, settable flags, but there is no `ApiKey` model, no hashed-key auth middleware, and no webhook dispatcher for them to actually gate yet.
- **Roles & Permissions is read-only in this pass**, and this is a deliberate, documented architectural decision, not an oversight: `rbac.service.js`'s `hasPermission()` is called **synchronously** from `authorizePermissions` middleware on every single permission-gated route in the entire application. Making role→permission truly live-editable through the (async, cached) settings engine would mean changing that hot-path check application-wide — judged to need its own dedicated, careful pass rather than being bundled into this one, where it could easily introduce a subtle app-wide auth regression.
- **SSO is scaffold-only**, matching the spec's own decision gate — no live SAML/OIDC handshake.
- **No Playwright browser-driven test suite.** All verification above is real (live HTTP calls, live database state, actual observed before/after transitions) but was performed via direct API/script calls, not literally "in a browser" as the spec's protocol asked for. INSZoom already has a Playwright e2e setup (`INSZoom/frontend/e2e/`) that the next pass should extend rather than introducing a second test framework.

## 6. What should not be done (going forward)

- (Superseded by §8.2 below — kept for the historical record) Do not make `rbac.service.hasPermission()` async without a dedicated pass. What actually shipped in §8.2 does **not** make it async: it stays a plain synchronous check against an in-memory map, and only that map's *contents* are refreshed asynchronously in the background via a `settingsEvents` subscription. The original caution about changing its call signature/contract still stands — that was never done and still shouldn't be.
- Do not delete or repoint the existing `Settings` singleton model. `entity-config`, `leads`, the eligibility quiz, and consultation booking all read from it directly today; the new engine is meant to sit alongside it, not replace it, until each of those is deliberately migrated over one at a time.
- Do not claim "verified in browser" for any category that hasn't actually been driven through a browser — everything verified so far (§4 and §8) is real HTTP/DB evidence, not literally in-browser.
- Do not introduce `node-cron` for future scheduled jobs in this codebase — follow the existing `setInterval` + `withJobLock` + `scheduleInitialRun` convention in `server.js` for consistency with every other recurring job already there (both new §8 jobs follow it).
- Do not write settings-engine writes for live-verification purposes from a standalone script while testing against the already-running dev server process — the in-memory `settingsCache` and (as of §8.2) `rbac.service`'s permission-override cache are per-process; a write from a different process never invalidates the serving process's cache. Always verify through the real REST API call made to the actual running server (see §4.3 and §8.2's own rediscovery of this same lesson).
- Do not add a new `AiUsageLedger` model if asked to build AI spend tracking here again — `AIJob.usage.{inputTokens,outputTokens,estimatedCost}` plus `ai-orchestration.service.js`'s existing `usage()` aggregation already *is* that ledger (see §8.1). Check for existing infrastructure before building a parallel one.

## 8. Phase 2 — 2026-09-17 session

A further implementation pass, prompted by a second detailed spec targeting the 7 gaps this report's §5 listed. Same rule as before: built for real, verified with observed evidence, reported honestly against what's actually done — not a claim of full completion of that spec either. ### 8.1 AI budget enforcement (spec's "G3")

**Problem:** `ai.budget.monthlyUsdCap` / `ai.budget.perUserDailyUsdCap` existed as registry entries with no runtime consumer — an AI call could never actually be blocked for exceeding budget.

**Circumstances analyzed — a real discovery that changed the approach:** the spec called for building a new `AiUsageLedger` model plus a hardcoded per-model cost table. Before doing that, `ai-orchestration.service.js` was read directly — it turned out an equivalent ledger **already exists**: every `AIJob` document already has `usage.{inputTokens, outputTokens, totalTokens, estimatedCost, latencyMs}`, populated from the real provider response, with cost computed per-provider-config (not a hardcoded global table — actually more flexible, since pricing can already differ per configured provider). A `usage(query)` aggregation function and an admin-only `GET /api/ai/usage` endpoint already existed too. **Decision:** did not build a second, parallel ledger. Added only the one real missing piece: a budget-cap check.

**Solution:** a `checkAiBudget(user)` function in `ai-orchestration.service.js`, called as the very first line of `callModel()` (before any provider is actually called) — checks org-wide monthly spend (via the existing `usage()` aggregation, date-filtered to the current month) against `ai.budget.monthlyUsdCap`, and per-user daily spend against `ai.budget.perUserDailyUsdCap`, throwing a `429 AI_BUDGET_EXCEEDED` / `AI_USER_BUDGET_EXCEEDED` before any model is invoked when over cap. Also fires a one-time-per-month (best-effort, in-memory-deduplicated) admin notification once spend crosses `ai.budget.alertThresholdPct`. Marked `retryable: false` on both thrown errors specifically — `execute()`'s existing catch block treats any `status === 429` as transiently retryable by default (correct for a real rate limit, wrong for a hard budget wall that will just hit the same cap again), so without this a background AI job would be pointlessly re-queued.

**Verification (real, live, with an honest caveat):** discovered along the way that the currently-configured Gemini provider (`gemini-2.5-flash`) is deprecated by Google and every real call to it fails — a genuine, pre-existing bug, unrelated to this work, **flagged here but not fixed** (touching production AI provider config wasn't asked for and carries its own risk). Worked around it correctly rather than being blocked by it: since the budget check runs *before* the provider call, seeded a real `$25` `AIJob` record for the current month, set the cap to `$10` below it, and called the real `/api/ai/search` endpoint — got a genuine `429 AI_BUDGET_EXCEEDED`, with the stack trace confirming the throw happened inside `checkAiBudget`, before ever reaching the broken provider call. Cleaned up the seeded record, test user, and restored the cap to `0` (disabled) afterward.

### 8.2 RBAC live-reload (spec's "G2")

**Why this was reopened:** the original report (§6) said not to make `hasPermission()` async without a dedicated pass. The new spec's own Option A resolved exactly that concern: keep `hasPermission()` fully synchronous, and instead maintain an in-memory role→permission-overrides map that's refreshed in the *background* whenever a setting changes. That's a materially different, much lower-risk design than "make the hot-path check itself async," so it was built.

**Circumstances analyzed — a require-cycle risk found and avoided:** the natural way to read the current setting value would be through `settingsEngine.service.js`'s `getEffective()`. But that module already `require()`s `rbac.service.js` (for its own write-permission checks) — requiring it back from `rbac.service.js` would create a circular `require()`, which Node resolves by handing back a partially-populated module at the point of re-entry, an easy way to get a silent `undefined` export depending on load order. **Decision:** `rbac.service.js` reads the `SettingValue` model directly (a leaf dependency) and subscribes to the plain `settingsEvents` `EventEmitter` (also a leaf dependency) — never touching `settingsEngine.service.js` at all, avoiding the cycle entirely.

**Solution:** added `roles.permissionOverrides` (JSON, per-role permission-list array) to `settings/registry/roles.registry.js` — a genuine *replacement* of a role's effective permission list when set (not a merge with the static baseline), since the verification scenario explicitly requires *revoking* a permission, not just granting new ones. `rbac.service.js` now loads this into an in-memory map at startup (fire-and-forget — a cold start is never blocked by it) and reloads it on every `settings.changed` event for that key. **Hard-coded lockout guard:** `hasPermission()` short-circuits to `true` for `role === "super_admin"` *before* ever consulting the override map, so no override value — malicious, buggy, or otherwise — can ever lock out the last super_admin.

**Verification (real, live, and a repeated methodological lesson):** the first attempt wrote the override via a standalone script — and got a **false "still 200" result** for the exact same per-process-cache reason documented in §4.3 (a write from one process doesn't invalidate a different process's in-memory cache). Recognized the pattern immediately this time and redid it correctly: created a real `case_manager` test user (confirmed baseline `200` on `/api/analytics`) and a real `super_admin` test user, then used the actual `PATCH /api/settings-v2` REST call (from the same live server process serving the test requests) to remove `analytics:read` from `case_manager` — the *same* token immediately got `403`, no restart. Restored the override to `{}` — `200` again. Additionally attempted to override `super_admin` itself down to an empty permission list via the same real API — the write succeeded (nothing rejects the write itself), but the super_admin test token **still got 200** on the next request, confirming the lockout guard held. All test users and the override value were cleaned up afterward. Re-ran the full authorization test suite (16/16 passed) — no regression from changing `rbac.service.js`, the single most load-bearing file in the app's request path.

### 8.3 SLA due-dates + breach detection (part of spec's "G4")

**What was built:** `Case.js` gained additive `slaDueDates: {intake, rfeResponse, docCollection}` and `slaStatus` (`on_track`/`at_risk`/`breached`) fields. A new `modules/settings/workflowSla.service.js` computes due dates from the live `workflow.sla.*` settings (plain calendar-day `Date` arithmetic — **no date library exists in this backend's `package.json` at all**, confirmed by checking before choosing an approach, so none was added), and a new hourly job (`startSlaSweepMaintenance()` in `server.js`, following the exact same `withJobLock`/`setInterval`/`scheduleInitialRun` shape as every other recurring job in that file — not `node-cron`, which remains unused in this codebase by deliberate choice, see §3) promotes cases to `at_risk` (due within 24h) or `breached` (already past due), firing a real notification to the assigned case manager on breach.

**Circumstances analyzed — why the wiring point was chosen carefully:** `case.controller.js`'s `createCase` is an 800+ line, transactional, multi-site case-creation function (two separate `Case.create()` calls, one for the principal case and one per child case) — the single most business-critical write path in the app. Rather than editing deep inside its transaction logic, the SLA due-dates were computed **once, just before** the already-existing `commonCaseData` object literal is built, and added as one new field to that object — the same object that's already spread into *both* the principal and child `Case.create()` calls. This means zero changes to the transaction's control flow, zero changes to any existing field's logic, and the computation is wrapped in its own `.catch(() => undefined)` so a settings-engine hiccup degrades to "no SLA dates set" rather than ever blocking case creation itself.

**Verification (real, live, end-to-end):** created a real case via `POST /api/cases` (as a real, promoted-to-admin test user) and confirmed in the database that `slaDueDates` exactly matched `createdAt + {7, 14, 10}` days — the then-current `workflow.sla.*` values. Changed `intakeMaxDays` to `1` via the live settings engine and created a second case — its `slaDueDates.intake` was exactly 1 day out, while the *first* case's stored value was untouched (confirming due dates are a creation-time snapshot, not a live-recomputed value, matching how every other "computed at creation" field on this model already behaves). Backdated the second case's `slaDueDates.intake` to yesterday, assigned it a case manager, and ran the sweep function directly — the case flipped to `breached`, a real `Notification` document was created for that case manager, and (as a bonus, unplanned confirmation) a *third*, unrelated case created moments earlier under the same 1-day SLA setting was correctly flagged `at_risk` by the same sweep, since its due date also fell inside the 24-hour window. All test cases, users, and notifications were deleted and the setting restored to `7` afterward. Re-ran the case-related test suite plus both phase0/phase1 regression suites (45/45 passed).

**Deliberately not done in this pass:** the assignment-strategy half of workflow (`round_robin`/`load_balanced` auto-assignment) was investigated but not implemented — `assignedCaseManager` in `createCase` is not an isolated value; `status`, `assignedAgent`, `agentEmail`, `assignedAgentUser`, and `primaryOwner` all derive from whether it was explicitly provided, across a function long enough that its full downstream usage wasn't read end-to-end in this pass. Wiring auto-assignment in correctly means resolving `assignedCaseManager` *before* that whole cluster of derived fields, which needs a complete read of the function first — the same "needs its own dedicated, careful pass" judgment already applied to the RBAC editor in the original report, here applied to this one specific sub-piece rather than the whole SLA/workflow gap (the due-dates half above was judged safe and separable, and was done).

### 8.4 Branding runtime and Integrations — investigated, deliberately not attempted

**Branding (spec's "G5"):** located the real PDF letterhead generator (`modules/form-generation/services/CoverLetterService.js` — a `{{dot.path}}` template renderer whose data context is assembled elsewhere, by an "orchestrator" the service's own comments reference but which wasn't traced through in this pass) and confirmed neither `branding.firmAddress`/`firmPhone`/`companyName` nor any hardcoded firm string appears in that file directly — meaning the actual wiring point is wherever that context object is built, not yet located. Wiring the CSS-variable side additionally requires touching both `INSZoom/frontend` and `Immiglance/Frontend`'s app-root theming. Given both halves require tracing unfamiliar code paths this pass didn't have budget to do carefully, this was left alone rather than guessed at.

**Integrations (spec's "G6"):** no `ApiKey` or `Webhook` model exists anywhere in the codebase (confirmed) — this is a genuinely new subsystem (models, key hashing, a rate-limited auth middleware, an HMAC-signing dispatcher with retry/auto-disable) on the scale of its own small feature, not a wiring task like the others in this section. Not started.

## 9. "Settings Overhaul" — 2026-09-17 session (later same day)

A third pass, prompted by a spec that **replaced the category taxonomy itself** — modeled on Docketwise/INSZoom's actual settings screens (Firm Profile, Users & Permissions, Client Portal, Notifications, Questionnaires & Intake, Email & Templates, Invoice & Billing, Security, AI Platform) rather than the more abstract/generic structure from §3–§4. The engine infrastructure (SettingValue/SettingsAuditLog/settingsEngine.service.js/REST API) was explicitly kept per this spec's own D1 — only the registry *content* changed.

### 9.1 A conflict found in the spec's own migration table, resolved before writing any code

The new spec's migration table said to **discard** `roles.permissionOverrides` and `data.retention.auditLogDays` as "abstract keys with no real UI anyway." That description was true when §3–§4 were written, but is no longer true after §8: both are now live, verified, working enforcement — `roles.permissionOverrides` backs the RBAC live-reload in `rbac.service.js` (§8.2), and `data.retention.auditLogDays` drives the hourly-checked retention sweep. Discarding them as instructed would have silently deleted working functionality. **Resolved by keeping both, unchanged, exactly where they already lived** (`roles.permissionOverrides` relocated into the new `users.registry.js`, `data.retention.auditLogDays` left in the untouched `data.registry.js`) rather than either blindly following the table or stopping to ask — the same category of judgment call as every other Phase-0-driven adaptation in this report, flagged here rather than silently made.

A second read of the same table showed most of its other renames (`security.session.idleTimeoutMinutes` → `security.sessionTimeoutMinutes`, `org.timezone` → `firm.timezone`, etc.) were genuinely safe, since nothing outside the settings UI (which doesn't exist yet) reads the *new* names either way. **Decision:** rather than rename the enforcement-critical keys purely for cosmetic consistency with a UI that isn't built yet (real regression risk for zero present benefit), the existing key names were left exactly as they are for every setting with a live consumer (idle timeout, password policy, retention, permission overrides, notifications, AI budget, feature flags, SLA). Only genuinely new settings (firm.\*, portal.\*, intake.\*, email.\*, invoice.\*, the two new lockout settings) use the new spec's naming convention, since there was no existing consumer to break.

### 9.2 What was built

- **Registry restructuring:** deleted `organization.registry.js`, `branding.registry.js`, `integrations.registry.js` (confirmed zero runtime consumers before deleting each one). ### 9.5 What should not be done (added to §6's list)

- Do not discard a registry key just because a spec's migration table calls it "abstract" or "no real UI" — verify against the actual current codebase first; both keys this pass almost discarded had become live, verified enforcement in the pass immediately before it.
- Do not rename an enforcement-critical settings key purely to match a new naming convention when no consumer of the new name exists yet (i.e., no frontend) — the regression risk (a missed call site silently breaking live enforcement) outweighs the cosmetic benefit until something actually needs the new name.
- Do not build a new CRUD module for a concept without first checking whether an empty, unmounted, or partially-scaffolded directory for it already exists (`modules/teams/` was empty and unmounted, not absent) — a quick `find`/`ls` before writing a new model would have been the very first move regardless, and was here.
